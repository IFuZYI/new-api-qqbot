# ADR-0010 — 日志分等级写入按天文件，并按保留天数自动清理

状态：已采纳（2026-10-12）

## 背景

在此之前，服务的运行记录只有一个出口：`log.Printf` 写到 stderr。这带来三个具体问题：

1. **失败看完就没了**。运营在群里遇到「发了绑定指令没反应」「签到没发奖励」，唯一能看的
   是终端当时那一屏；容器重建或日志驱动轮转之后，现场就消失了。
2. **没有等级**。要排查问题就得先把噪音全开，而平时这些噪音又必须关掉——两者不可兼得。
3. **文件会一直涨**。即使有文件，没有任何机制删除旧文件。

## 决策

**日志是服务的一个一等功能：等级可配、按天落盘、过期自动清理，面板里可读。**

### 双出口：按天文件 + 进程控制台

每条记录同时写两处：

- `<data>/logs/qqbot-YYYY-MM-DD.log`：JSON 一行一条，供面板读取与清理；
- stderr：文本格式，`docker logs` / `journalctl` 照旧可用。

两个出口共用同一个等级。文件按**天**切分，而不是按大小：保留策略以「天」为单位，
按大小切分的文件无法回答「这是哪天的」。切分在 `Write` 内部按当前时钟判断，slog 一次
`Write` 写一条完整记录，所以换日不会把一条记录劈成两半。

### 等级：INFO 与 DEBUG，作用于全部出口

| 等级 | 记什么 |
|---|---|
| `ERROR` | 巡检失败、5xx 响应、panic（含堆栈）、写库失败 |
| `WARN` | 可继续但需要知道：绑定指令失败、进群绑定失败、事件流断开、设备指纹不可用 |
| `INFO` | 状态变化：启动、事件流连接、绑定成功、记录签到、清理日志 |
| `DEBUG` | 每一次 API 请求、每一个事件、每次巡检完成、跳过的签到 |

`INFO` 是默认值，也是面板给出的唯一选项之一；`WARN`/`ERROR` 在两种等级下都写。
**等级保存在设置里，保存后立即应用到正在运行的 logger**——排查问题的人不会为了打开
DEBUG 而重启服务，而重启恰好会丢掉他要观察的状态。启动时与每小时一次维护循环会重新
应用一次，因此配置文件或别处的改动也会被采纳。

### 失败必须是结构化记录，不能只是文本

「按钮点了没反应」的定位依赖属性，而不是句子。因此失败记录一律带结构化字段：

- 巡检失败：`patrol` + `err`（`Sweep` 的 record 是唯一入口，定时器与「测试一次」都经过它，
  所以手动执行失败同样会出现在 ERROR 里）；
- 5xx 响应：`method`/`path`/`status`/`duration_ms`/`err`——中间件在响应写完后记录，
  并把 `writeErr` 拿到的真实错误（客户端只看到「服务器内部错误」）附在同一条记录上；
- panic：`panic` + `stack`。

4xx 只在 DEBUG 记录：那是调用方的输入问题，让它占满 ERROR 视图会让真正的问题被淹没。

### 保留天数：0 表示永久，只删自己写的文件

`log_retention_days` 含今天（`7` = 今天加前 6 天），`0` = 永久保留。删除发生在启动时
与每小时一次的维护循环里，不是每条日志都去扫目录。**只匹配 `qqbot-YYYY-MM-DD.log`
且日期能解析的文件**：运营可能把导出的副本或笔记放在同一目录，模糊匹配会把它们一起删掉。
日期取自**文件名**而不是 mtime——拷贝或恢复目录会重置 mtime，而文件名才是「这一天」的
权威来源。

### 面板只读，设置只影响记录什么

「日志」页按日期/等级/关键字查询，过滤在服务端完成（DEBUG 的一天可能有几十兆）。
返回体里同时带**当天各等级的总条数**（不受过滤影响），因此列表过滤到 WARN 时，
「今天 3 条 ERROR」仍然成立。日志内容本身不可从面板修改或删除。

### 「今天」是运营的今天，不是主机的今天

日志按天切分，而**哪一天由设置里的时区决定**，与签到、奖励用的日界完全一致。
这一条不是理论问题：主机跑 UTC、运营设 `Asia/Shanghai` 时，北京时间 00:30 写的记录
会被归到前一天的文件里，保留边界也会在早上 8 点滚动——与面板上显示的签到日期对不上。
`logging.Options.Location` 由 `cmd/qqbot` 从设置读出，启动时应用一次；
面板返回的 `tz` 字段让前端用同一个时区渲染时间，否则浏览器会把「10-13 的记录」
显示成「10-12 15:54」，正是这条规则要避免的混乱。

### 记录里不写群聊内容

DEBUG 会记录「收到了什么事件」，但只记**结构**（`post_type`/`notice_type`/`group_id`/
`user_id`/`message_type`/字节数），不记原始 JSON。原始事件含 `raw_message` 与
`sender.nickname`：日志文件长期保存且面板可搜索，把成员发言写进去等于把群聊内容落盘。

### 保留键位（time/level/msg/source）不能被属性占用

属性名与 slog 自己的键位重名会写出**重复 JSON 键**，解码只保留最后一个——
一条带 `level` 属性的记录会因此读不出自己的等级、从面板里消失。
`attrRenamer` 包装 handler，把冲突的属性改名为 `#level` 之类，记录保持可读。

### 查询不做全量解码

DEBUG 的一天可以有几十兆。查询先用字节扫描取出每行的 `level`（统计需要它），
只有可能被返回的行才做完整 JSON 解码。实测 22MB / 16 万行：**917ms → 36ms**。
搜索只匹配消息与属性值，不匹配原始行——否则搜 `502` 会命中时间戳里的纳秒数字。

### 日志目录属于数据目录

`<data>/logs/`，与 `qqbot.db`、`config.yaml` 同级：备份数据目录就带走了日志，
容器只需要挂载一个卷。目录不存在时自动创建。

## 影响

- 新增 `internal/logging`：`Manager`（等级 + 双出口）、按天文件、清理、查询、维护循环。
  它不依赖 `internal/service`（避免循环引用），启动时由 `cmd/qqbot` 把设置读成 `Policy` 喂给它。
- 进程默认 logger 被替换为同一个 handler（`slog.SetDefault` 同时把标准库 `log` 接进来），
  因此历史调用点与任何依赖的日志也进入按天文件；已有调用点已改为带等级的 `slog`。
- 设置新增两个字段（`log_level`、`log_retention_days`），旧 blob 缺字段时回落到默认值。
- 非法等级在保存时返回 400，而不是静默变成 INFO——「以为开着 DEBUG」是最难发现的配置错误。
- 服务层（绑定、奖励、分组转换）的失败也记日志：计数在面板上，**原因**只有日志里有。
- 等级切换本身记一条 INFO（同样的策略不重复记），运维切换后能在日志页看到确认。
- `limit=0` 表示「不限制」，缺省参数才是默认上限。
