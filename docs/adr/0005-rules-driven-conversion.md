# 0005 分组转换由规则驱动，不是一刀切

分组转换不再是「把 default 组的人提升到 authorized」这一条硬编码逻辑，而是管理员配置的
**规则**：每条规则有自己的触发方式（绑定成功时、巡检周期、或两者）、源分组（可多选）、
目标分组、以及可选的条件（群等级 / QQ 等级 / 入群天数 / 累计签到天数 / new-api 余额 /
new-api 请求数）。条件之间是「且」。

原因：需求从「default → authorized」演变成了「选择触发条件、源分组可多选、目标分组」，
而「谁该被转换」本来就是运营决策，不该写死在代码里。硬编码版本还有第二个问题：它和规则
机制并存时，成员巡检每轮都会调用一次旧的一刀切提升，**绕过规则**把账号搬走 —— 实测中
确实发生了，管理员看到的规则配置与系统实际行为不一致。因此旧路径已删除，转换只有一个
决策点。

两条约束，都是为了让半成品规则不能造成破坏：
- 既没有触发方式、也没有条件的规则视为**未完成**，不匹配任何人（否则它等于「所有人」）。
- 有触发方式但没有条件 = 明确的「所有绑定成员」，这是允许的。

写入前按 id 重读账号（new-api 的更新是覆盖式的，稀疏对象会清空 `display_name`），
并且源分组之外的账号一律不动。
