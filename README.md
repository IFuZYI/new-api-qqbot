# QQBot 群监测

把 QQ 群成员身份与 [new-api](https://github.com/Calcium-Ion/new-api) 账号关联起来的监测服务。

它镜像群成员名单与每日签到榜，按成员的 QQ 邮箱（`qq@qq.com`）把每个人绑定到对应的
new-api 账号，按规则把账号从源分组提升到目标分组，并发放每日签到奖励。

**只读群、不在群里发言**，唯一例外是响应成员发来的绑定与签到指令（指令内容由运营在面板里配置）。

---

## 功能

| 功能 | 说明 |
|---|---|
| 群成员同步 | 从 NapCat 读取机器人所在群的成员名单，成员以 QQ 为主键、**永不删除** |
| 自动绑定 | 用 `qq@qq.com` 精确匹配 new-api 账号；0 个 → 未绑定，多个 → 不猜、留待人工 |
| 绑定指令 | 成员在群里发指令（默认 `/绑定`、`<绑定>`、`>>绑定<<`，可自定义、支持正则）即绑定到 `他的QQ@qq.com` 对应账号 |
| 进群自动绑定 | 成员加入监测群时立即按同一规则匹配并绑定 |
| 绑定巡检 | 周期性重试所有未绑定成员，补上「先进群、后注册」的账号；周期可配 |
| 手动换绑 | 面板里从**任一侧**发起：选 QQ 或选账号，两侧都是下拉选择；**解绑前弹确认框**（写明 QQ、账号与「无法撤销」） |
| 分组转换 | 规则驱动：触发方式用**复选框**选择（绑定成功时 / 按巡检周期，可同时勾选）+ 源分组 + 目标分组 + 可选条件；**删除规则前弹确认框** |
| 签到记录 | 两条来源写同一行：打卡榜轮询（带排名）与群消息（指令或任意消息，可配）；按 `(qq, 日期)` 幂等，多轮结果是**并集**；**未绑定成员不记签到**（奖励发不出去），绑定后下一轮补记 |
| 签到奖励 | 每天每人一次，额度（单位 new-api 的 **quota**）在 `[下限, 上限]` 内随机；首次抽取即持久化；明确拒绝可按原额度重试，结果不明保留领取占位待核对 |
| 用户目录 | 以 **QQ 与 new-api 账号双键**取并集，回答「谁没进群」；显示今日签到的来源 |
| 连接测试 | 逐通道探测（new-api 登录 / NapCat WebUI / OneBot HTTP / 事件 WS），失败时指明是哪一段 |
| NapCat 自动配置 | 只填 WebUI 地址即可自动开启 OneBot 适配器并回填连接信息（热改，无需重启） |
| 运行日志 | 每条记录同时写按天文件与进程控制台；等级 `INFO`/`DEBUG` 可在面板切换（立即生效）；保留天数可配（`0` = 永久），过期文件自动清理 |

**每一类自动化都有独立开关**（绑定指令 / 进群绑定 / 绑定巡检 / 消息签到 / 打卡榜巡检 /
群成员巡检），关掉的自动路径不会产生请求。**三条自动绑定路径**（指令、进群、巡检）只处理
**未绑定**成员，不覆盖手动换绑；管理员可手动换绑。**签到路径相反，要求成员已经绑定**。

界面为简体中文。

## 架构

```
cmd/qqbot/          入口、参数、按需重建的客户端
internal/store/     SQLite 表结构、迁移、查询
internal/service/   业务逻辑，只依赖 Gateway / QQ 两个接口
internal/command/   指令解析与匹配（字面量 + 正则）
internal/newapi/    new-api 管理 API 客户端
internal/napcat/    OneBot HTTP 客户端 + NapCat WebUI 桥
internal/events/    OneBot WebSocket 监听（指令、进群、消息签到）
internal/api/       HTTP 接口、鉴权、静态文件
internal/config/    连接配置（文件 + 数据库双份）
internal/scheduler/ 按路径拆分的独立巡检
web/src/features/   面板按功能拆分的模块
web/                React + Vite + Tailwind 面板
docs/               设计共识、ADR、审计记录
```

**外部依赖只有两个**：new-api 网关（HTTP API）与 NapCat（QQ 侧）。

## 快速开始

### 方式一：Docker Compose（推荐）

```bash
git clone git@github.com:IFuZYI/new-api-qqbot.git
cd new-api-qqbot

cp .env.example .env
# 编辑 .env，至少设置 QQBOT_ADMIN_PASSWORD（≥8 位）
# 面板管理密码。留空则首次打开面板时用表单创建。

docker compose up -d --build
```

打开 `http://<主机>:4096/`，登录后在「连接配置」里填写 new-api 与 NapCat。

数据（SQLite 库 + `config.yaml`）存在 Compose 逻辑卷 `qqbot-data` 里，容器重建不丢。
**实际卷名通常为 `<项目名>_qqbot-data`，不是裸 `qqbot-data`**；不要为了套用备份命令给卷
新增固定 `name:` 或更改项目名，那会挂到另一只空卷，看起来像生产数据消失。

以下在 Bash 中从部署目录执行，需要 Python 3。`dc` 必须与部署时使用相同的 `-p`、`-f`、
`--env-file` 参数（包括 override 文件）；没用过这些选项就保持示例。先从有效配置解析实际卷名，
并确认卷已存在，避免备份命令悄悄创建空卷。备份和恢复都通过 **qqbot 服务自身的挂载**访问数据。

```bash
set -euo pipefail
dc() { docker compose "$@"; }  # 如部署用了 -p mybot，在这里也加上
volume=$(dc config --format json | python3 -c 'import json,sys; c=json.load(sys.stdin); mounts=[v for v in c["services"]["qqbot"]["volumes"] if v["target"]=="/app/data"]; assert len(mounts)==1 and mounts[0]["type"]=="volume", "unexpected data mount"; print(c["volumes"][mounts[0]["source"]]["name"])')
docker volume inspect "$volume" >/dev/null
printf '数据卷：%s\n' "$volume"
# 核对与现有部署一致后继续；确认没有其他容器或进程写入该卷。

# 离线备份：先停服务，SQLite 主文件、WAL/SHM 与配置一起归档。
umask 077
dc stop qqbot
dc run --rm --no-deps -T --user 0 --entrypoint tar qqbot \
  czf - -C /app/data . > qqbot-data.tgz.part
tar tzf qqbot-data.tgz.part >/dev/null
mv qqbot-data.tgz.part qqbot-data.tgz
dc start qqbot
```

这是**离线一致性备份**，不可在服务仍写入时直接 tar SQLite 文件。失败时保持服务停止、排查后再启动；
不要使用 `docker compose down -v`。备份含密码、会话与指纹密钥，需限制权限并加密异地保存；
部署用的 `.env` 不在卷内，要另行安全备份。已有同名归档会被覆盖，请先移走旧备份。

恢复会**清空实际卷中的现有文件**。先用上面步骤把现状另存为独立的回滚备份，再在同一 Bash 会话
中执行下面的恢复；若新开终端，先重新执行 `set`、`dc`、`volume` 与检查步骤。归档必须来自可信来源。

```bash
# qqbot-data.tgz 是要恢复的归档，不是刚做的回滚备份。
tar tzf qqbot-data.tgz >/dev/null
docker volume inspect "$volume" >/dev/null
dc stop qqbot  # 恢复前必须停止，且没有其它写入者
# 清掉旧 WAL/SHM 等残留，避免把两个数据库快照混在一起；tar 保留归档中的属主。
dc run --rm --no-deps -T --user 0 --entrypoint sh qqbot -ec \
  'find /app/data -mindepth 1 -maxdepth 1 -exec rm -rf -- {} +; tar xzf - -C /app/data' \
  < qqbot-data.tgz
dc start qqbot
# 登录面板，核对群、绑定与签到数据；不要仅凭 HTTP 健康就认定恢复成功。
```

> 卷里还有 **new-api 的登录会话与设备指纹密钥**，所以**保留这个卷**（含重建容器、升级镜像）
> 意味着服务不必重新登录 new-api —— 直接复用那条 30 天有效的会话，不占账号的会话名额。
> 把卷删掉/不挂载则每次启动都会重新登录一次。

> **网关开了 `SESSION_COOKIE_SECURE=true` 时**（new-api 的启动警告建议生产环境打开），它的刷新
> 接口会校验请求来源。本服务已经按配置的网关地址发送同源 `Origin`，所以正常可用；但若网关在
> **终止 TLS 的反向代理**后面，new-api 判定 scheme 时不看 `X-Forwarded-Proto`，运营需要把对外的
> 网关地址填进它自己的 `SESSION_COOKIE_TRUSTED_URL`（否则连它自己的网页面板也过不了这道校验）。
> 若地址填错，刷新会被拒（`AUTH_ORIGIN_FORBIDDEN`）——面板的「连接测试」会直接报出来。

### 方式二：直接运行二进制

需要 **Go 1.27.2 或更新的受支持安全版本**（标准库安全修复）及 Node.js 22 / npm。
全新克隆不带 `web/dist`，要使用面板必须先安装并构建前端；Docker 构建会自动完成这一步。

```bash
(cd web && npm ci && npm run build)
go build -o qqbot ./cmd/qqbot
./qqbot -addr :4096 -data data -web web/dist
```

之后修改前端也需重跑上述前端构建。若只用 API，可以不装 Node、不构建前端；
缺少 `web/dist` 时服务显示说明页，而不是完整面板。已有二进制也必须用安全版本 Go 重新构建，
只升级宿主机 Go 不会修复旧二进制内的标准库。

## 配置

### 面板管理账号

首次打开面板会要求设置管理账号（本项目自己的账号，与 new-api 无关）。之后同一表单用于登录。

也可以在 `.env`（**仓库根目录**，与 `.env.example` 同级）里预置，适合无人值守部署：

```bash
QQBOT_ADMIN_USERNAME=admin
QQBOT_ADMIN_PASSWORD=至少8位
QQBOT_PORT=4096
```

服务在**开始接受请求之前**读取它，所以新实例不会有一瞬间对先到者敞开。这是密码丢失时的
恢复路径：改值、重启即重置。**留空 = 不动已有账号**，所以模板里的空行不会清掉密码。

优先级：显式 `-addr` 参数 > `QQBOT_PORT` > 默认 `:4096`。

### 连接配置（面板里填）

| 项 | 说明 |
|---|---|
| new-api URL / 账号 / 密码 | 需要一个**管理员**账号（能改用户分组与额度） |
| NapCat WebUI 地址 / Token | 面板地址，如 `http://127.0.0.1:6099`；填好后可点「自动配置」 |
| OneBot HTTP URL / Token | 巡检调用动作走这里，自动配置会填好 |
| 事件 WebSocket URL / Token | 接收进群、绑定指令与消息签到；留空不影响成员/打卡榜巡检，但指令与消息签到不可用 |

配置同时写入 `data/config.yaml` 与数据库，两种改法都有效且不会互相覆盖：

- 手改 `config.yaml` → 服务**下一次读取时**采用，**不需要重启**
- 在面板保存 → 同时写入数据库与该文件

> `config.yaml` 里密码与 token 是明文（否则无法回写），权限为 `0600`。

### Docker 下的 NapCat 地址

NapCat 通常跑在宿主机上，容器内的 `127.0.0.1` 指向容器自己。所以容器里填地址要用
`host.docker.internal`：

```
WebUI 地址     http://host.docker.internal:6099
OneBot HTTP    http://host.docker.internal:3002
事件 WebSocket ws://host.docker.internal:3001
```

`docker-compose.yml` 已加 `extra_hosts: host.docker.internal:host-gateway`，Linux 上可用。

**还要改 NapCat 侧的监听地址**，这一步最容易漏：

| 组件 | 需要监听 | 原因 |
|---|---|---|
| NapCat WebUI | `0.0.0.0`（默认已是） | 容器要能连到面板 |
| OneBot 适配器 | **`0.0.0.0`** | 默认只绑 `127.0.0.1`，容器**永远**连不上宿主回环 |

OneBot 适配器可以在「连接配置 → NapCat → 自动配置 → 高级选项 → **适配器监听地址**」里填
`0.0.0.0`，服务会按这个地址改写 NapCat 的适配器配置。**服务返回并保存的连接 URL 仍会是可拨号
的地址（不是 `0.0.0.0`）**，两者是分开的：绑定地址决定"谁能连进来"，URL 决定"往哪连"。

> 暴露适配器前请确认 OneBot token 不为空——绑 `0.0.0.0` 意味着同网络的其他机器也能访问它。

## 运维

### 监测设置（面板）

页面按功能分区，每一块都有自己的开关；关掉的功能不会产生任何请求。

「监测设置」页按**触发方式**分两组：上半部分是**事件驱动**的路径（绑定指令、进群自动绑定、
消息签到），由群里的动静触发；下半部分是一张**定期巡检**卡片，把所有巡检的开关、周期与运行
状态放在一起，所以「哪些在按周期跑、还健康吗」一眼可见。分组转换按每条规则自己的周期运行
（在「分组转换」页配置），在这张卡片里只显示状态。

每条巡检行都有一个**测试一次**按钮：立即执行该巡检的真实巡检体（与定时器跑的是同一段代码），
并把本次结果写在行内（如「新绑定 2 人，待注册 1 人」「发放奖励 0 人，未绑定跳过 3 人」）。
手动执行同样会被记录，所以行上的健康徽标与「上次运行」时间随即更新，不会停在「尚未运行」。
**关掉开关的巡检也能手动测试一次**——「关掉的功能不产生请求」说的是自动循环，点按钮是一次
明确的请求，也是运营在打开开关前先试一次的方式；测试不会改变定时器的状态。

| 设置 | 默认 | 说明 |
|---|---|---|
| 绑定指令 | 开 | 指令列表可自定义（一行一个，`/表达式/` 为正则） |
| 进群自动绑定 | 开 | 成员进群时立即按 QQ 邮箱匹配 |
| 绑定巡检 | 开，60 分钟 | 周期性重试未绑定成员；间隔 0 = 暂停定时（保留开关状态） |
| 消息签到 | 开 | 触发方式为「按指令」（默认 `/签到`、`<签到>`、`>>签到<<`）或「任意消息」 |
| 打卡榜巡检 | 开，30 分钟 | 打卡没有事件通知，只能轮询；**关闭后只是不再从打卡榜记录签到**，消息签发的奖励照发；间隔最小 1 |
| 签到奖励区间 | 100–200 quota | 单位是 new-api 的 quota（默认 500000 quota = $1，换算随实例设置）；每天每人在区间内随机；上下限相同即固定 |
| 群成员巡检 | 开，120 分钟 | 兜底；新成员进群与绑定成功会立即记录；间隔最小 1 |
| 时区 | `Asia/Shanghai` | 决定「今天」的边界 |
| 日志等级 | `INFO` | `INFO` 记录状态变化与失败；`DEBUG` 额外记录每一次 API 请求与收到的每个事件。保存后立即生效，无需重启 |
| 日志保留天数 | 7 | 含今天；`0` = 永久保留。服务启动时与每小时清理一次，只删自己写的 `qqbot-YYYY-MM-DD.log` |

指令先忽略消息前后空格。**字面量**必须与整条消息完全一致，例如 `/签到`。
`/表达式/` 与 `/表达式/i`（忽略大小写）是正则，使用**搜索匹配**，默认不要求整条消息匹配：
`/签到/` 也会匹配「今天签到成功」。需要整匹配时显式加 `^`、`$`，例如 `/^签到$/`
或 `/^checkin$/i`。非法正则在保存时返回 400。签到指令列表**留空**表示任意消息都算签到。

### 日志

服务把每条记录同时写到**两份**：数据目录下的按天文件 `logs/qqbot-YYYY-MM-DD.log`
（JSON 一行一条）与进程控制台（文本格式，`docker logs` / `journalctl` 照旧可用）。
等级在「监测设置 → 日志」里切换，`INFO` 是默认值；`DEBUG` 打开后，每一次 API 请求、
每一个收到的 OneBot 事件、每一次巡检完成都会记下来。

面板的「日志」页直接读这些文件：可选日期、按等级过滤、按关键字搜索（匹配消息与属性值，
例如 QQ 号或错误串），并显示当天各等级的总条数。过滤在服务端完成，所以文件很大时也不会卡
（22MB 的一天实测 ~30ms）。页面按**设置的时区**渲染时间与「今天」，与签到日期一致。

日志只记事件的结构（谁、在哪个群、什么类型），**不记群消息原文与昵称**：文件长期保存
且可搜索，把群聊内容落盘不是这个功能该做的事。
失败记录带结构化属性——`巡检失败` 带 `patrol` 与 `err`，5xx 请求带 `path`/`status`/`err`
——这正是「按钮点了没反应」时用来定位的那条线。

| 等级 | 记什么 |
|---|---|
| `ERROR` | 巡检失败、5xx 响应、panic（含堆栈）、写库失败 |
| `WARN` | 可继续但需要知道的事：绑定指令失败、进群绑定失败、事件流断开重连、设备指纹不可用 |
| `INFO` | 状态变化：启动、配置管理员、事件流连接、绑定成功、记录签到、清理日志 |
| `DEBUG` | 每一次请求、每一个事件、每次巡检完成、跳过的签到 |

保留天数到期后，旧文件在启动时和每小时一次的维护循环里被删除；`0` 表示永久保留。
只匹配自己写出的文件名，目录里手工放的其他文件不会被删。日志目录是数据目录的一部分
（`<data>/logs/`），备份数据目录时日志会一并带走。

### 手动触发

面板「概览」页可立即执行：同步成员、自动绑定、分组提升、同步打卡、发放奖励、**手动签到**
（为选定的群成员记录一次消息签到，用于验证「消息即签到」这条路；同一天只记一次）。

### 健康检查

```bash
curl -s http://127.0.0.1:4096/api/auth/state
# {"authenticated":false,"needs_setup":false,"username":""}
```

该接口无需登录，足够判断 HTTP 服务是否存活（容器 HEALTHCHECK 用的就是它）。

`GET /api/status`（需登录）返回每条巡检的上次运行时间与错误，连同设置一起返回：只看时间
无法区分「还没跑」与「已停用」。

go build ./...                  # 编译

## 已知限制

- **new-api 管理员不能管理同级或更高级账号**（网关规则，不是缺陷）。验证时用普通账号（role 1）。
- **new-api 有活跃会话上限**（默认 50，有效期 30 天）。本服务的策略是**整个生命周期只登录一次**：
  登录后用刷新令牌（`POST /api/user/auth/refresh`）不断换取访问令牌，不再重复登录，所以常驻运行
  不会自己占满额度。会话（刷新令牌）**按「网关地址 + 账号 + 密码」绑定后落库**，重启直接复用、
  不占新额度；会话被撤销或过期时才真正重登一次。已实测：冷启动 1 次登录，之后跨令牌过期与多次
  重启都是 0 次登录（全部走刷新）。
  额度被占满时登录返回 `AUTH_SESSION_LIMIT`，面板会直接提示「请撤销其他登录会话或等待其过期」。
  改地址、改账号或改密码后旧会话都不再被加载（凭据只属于签发它的那一组配置），代价是改配置后重新登录一次。
- **每次请求都带一个稳定的设备指纹**（首次使用时生成并落库的独立密钥，随 `User-Agent` 发出，重启与重建容器都不变）。
  网关会把 `User-Agent` 记在会话行上，所以会话列表里这条**可辨认**——运营能看出哪个是本服务、该撤销
  哪一个，而不是面对一串匿名条目。指纹不采集宿主机的任何硬件信息，也不需要任何配置。
- **登录接口有频率限制**（`CRITICAL_RATE_LIMIT`，默认每 IP 每 20 分钟 20 次）。被限流时网关返回
  空的 429 与 `Retry-After`；本服务会识别它、显示需等待的时间，并在窗口内**不再尝试登录**，
  避免自己的重试把锁定期越拖越长。没有会话时不会先去试一次注定失败的刷新（刷新接口同受该限流），
  而是直接登录。
- **NapCat WebUI 凭证**默认用进程级密钥签名，NapCat 重启后失效，本服务会重登（有频率限制）。
- **`localhost` 会被规范成 `127.0.0.1`**：OneBot 适配器只监听 IPv4 回环，而 `localhost` 常先解析到
  `::1`，两者不通。
- **打卡榜的日期由 NapCat 决定**（它用 UTC 日期查询），在 UTC 与本地日期不同的时段可能查错日期。
- 签到榜的 `rank` 是 NapCat 换算过的值，只作展示，不是稳定标识。
- **消息签到依赖事件流**（WebSocket）。事件流断开时消息签到不会记录，但打卡榜巡检与奖励
  发放不受影响；「任意消息」模式下若事件流长期不可用，会表现为签到偏少而不是出错。
